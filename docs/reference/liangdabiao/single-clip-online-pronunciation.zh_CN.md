# 一次一个短 clip：发音为什么走在线，而这件事只需要播放器的一小片

记录于开发[英语词典应用](english-dict/README.zh_CN.md)期间。听不到音的词典是听不见的词典，
所以发音是硬需求 —— 而算账就把「存在本地」这条路否掉了。这篇写逼出在线方案的那笔容量账，
以及**只从一个大得多的现成播放器里取一小片**这个刻意的决定。

## 先算容量账

给全部 19,513 条词存音频，放不下，差两个数量级：

| 编码 | 每条 | 整个词库 |
| --- | --- | --- |
| 48 kHz 单声道，67 kbps MP3 | 约 9~16 KB | 200 MB+ |
| 8 kHz ADPCM，4 bit | **4.8 KB** | **约 94 MB** |

Flash 是 8 MB，其中大概 7.9 MB 可以给内容。压到 4.8 KB 那一列已经是谁都不会发货的音质下限，
而它仍然**大了 12 倍**。所以这不是「在线更好看」，而是唯一选项；它的代价 —— 设备必须联网 ——
是兄弟应用早就付过、也早就有配网流程的代价。

## 真正去取的是什么

一个词一个短 clip，来自有道的公开接口：

```
http://dict.youdao.com/dictvoice?type=0&audio=<word>   （type=0 美音）
```

一个 clip 1~2 秒、约 10 KB MP3。链路是 HTTP → `esp_audio_simple_dec`（纯软件 MP3）→ I2S，
而装一个 clip 的缓冲是一段**静态的约 9 KB**，初始化时分配一次、此后不释放。发音是这个应用的
核心操作，一天可能触发几百次；那么频繁地分配/释放 9 KB 只会把堆切碎、换不来任何好处；
而且与收音机那位兄弟不同，这里没有哪一刻是配网门户需要把这块钱要回去的。

## 从那个大播放器里只取四样，其余留下

兄弟应用里的播放器有 1290 行。其中绝大部分是在解决「边下边播一节 20 分钟课程」特有的问题：
分段预取、16 KB 环形缓冲、断点续取、段级退避重试、换台抢占。把它们摞在 10 KB、1.2 秒的
短音频上，不是「更稳妥」，而是**一堆根本不会发生的故障模式**，每个都要代码去维护。

保留的恰好四样：

1. **解码链路本身** —— HTTP → `esp_audio_simple_dec` → I2S。
2. **`esp_http_client_is_complete_data_received()` 加 `Content-Length`**，用来分清「播完了」
   和「断流了」。在两种情况下从 socket 读到的都是 0，而它们需要完全相反的后续处理 ——
   所以这是一条被刻意留下的判据，不是一处优化。
3. **音频产出看门狗。** 真机上最难查的故障是「界面显示正在播放、喇叭一声不响」——
   一行日志都没有，声音就那么没了。播放器钉住「最后一次成功写进 I2S 的时刻」，
   超时就把这次播放判失败并记录原因。
4. **「写失败必须打日志」。** 兄弟那位第一版播放器是静默 `continue`；声音没了、日志也是空的。

## 另加三样，因为这是一台靠按键驱动的设备

- **请求防抖。** 三颗按键是 ADC 分压共用一个 GPIO，所以接触抖动和用户连点，在软件层看起来
  一模一样 —— 而每个请求都是一次完整的 HTTP 往返。同一个词在 400 ms 内的两次请求合并成一次。
- **可取消。** 翻面、返回或换一个词，必须能立刻放弃正在跑的网络读，而不是等它自己超时
  （最多 4 秒），让界面僵在那儿。
- **剥 ID3v2 头。** 这个接口的 MP3 以 `ID3\x04`（ID3v2.4）开头；直接喂给解码器会先失步一段。
  头部长度写在同步安全整数里，自己剥掉比让解码器去试错可靠。

## 状态，以及界面被告知了什么

只有一条播放任务，同一时刻处理一个词，并上报五态 —— `IDLE`、`LOADING`、`PLAYING`、`DONE`、
`FAILED` —— 于是词条页能在音标旁边画一个二到四字的提示（加载 / 播放 / 失败）。
`wd_audio_play_word` 对**不算错误**的情形返回 `false` —— 没网、空词、同一个词正在播、
或落在 400 ms 窗口内 —— 界面在这几种情况下都保持安静，因为它们都不是读者需要被通知的事。

换词是**抢占**：上一个 clip 直接作废，而不是让它放完 —— 读者已经翻到下一个词了，
再听上一个词放完只会让人困惑，而不是有帮助。
